13 ноября 2026 года после обновления трёхузлового Proxmox VE один узел временно видел только собственный голос. Corosync потерял связи с двумя соседями, HA ждал кворума, а Ceph одновременно сообщал о расхождении часов, недоступном OSD и старых ключах CephX. Сначала нужно было вернуть связность и репликацию. При ротации следующей задачей стало переподключение клиентов RBD, которые продолжали работать со старым ключом.

В журнале обновления зафиксированы pve-manager 9.2.26, ядро 7.0.14-28-pve и Ceph Squid 19.2.7. В кластере три MON, один OSD на узел и 33 группы размещения (PG). Гостевые диски размещены на RBD.

## Что пришлось разбирать после обновления

| Симптом | Что показала проверка |
| --- | --- |
| Один голос из трёх, KNET пишет `has no active links` для двух соседей, `pve-ha-crm` переходит в `wait_for_quorum` | В журнале появились события `link: 0 is up` для обоих соседей. Состав вернулся к трём узлам, затем журнал зафиксировал ещё один кратковременный выход и возврат участника. Первопричина сетевого сбоя осталась неизвестной. |
| `clock skew` двух MON, расхождение около 0,46 с | В журнале `chronyd` зафиксирован выбор источника времени. В последующем `ceph health detail` предупреждение о часах исчезло. |
| Один OSD `down`, 33 PG `degraded` | В журнале запуска есть активация OSD через `ceph-volume`. Затем `ceph osd tree` показала три OSD `up`, а `ceph -s` подтвердил три `up/in` и 33 `active+clean`. По состоянию PG стало видно, что репликация восстановилась. |
| `ceph-crash` получает `Permission denied` при чтении административного keyring в `/etc/pve/priv` | В ходе миграции штатный помощник обновил ключ `client.crash`. Возобновление отправки crash-отчётов требует отдельного подтверждения по журналу сервиса. |

У Corosync и Ceph разные механизмы кворума. `pvecm status` показывает голоса Proxmox, от которых зависят кластерное управление и HA. `ceph quorum_status` показывает состав MON. Состояние репликации проверяется по OSD и PG. Эти команды позволяют снять показания после загрузки каждого узла.

```bash
pveversion
uname -r
pvecm status
ha-manager status
ceph versions
ceph quorum_status -f json | jq '{quorum_names, quorum_leader_name}'
ceph -s
ceph health detail
ceph osd tree
```

Ceph Squid начиная с 19.2.6 проверяет старые типы ключей и билетов CephX после исправления CVE-2025-30156. В этом случае менялся шифр ключей аутентификации и сервисных билетов. Формат и содержимое RBD-томов сохранялись.

## Как прошла ротация CephX

1. **Ключи кластера и новые билеты.** После восстановления кворума и репликации проверили план штатного помощника `/usr/share/pve-manager/migrations/pve-cephx-rotate-service-keys` и применили `--rotate-cluster-keys --apply` на одном узле. Этот этап охватил MON, MGR, OSD, bootstrap и crash. MON перезапускались по одному и возвращались в кворум. Три OSD подтвердили новый тип ключа без перезапуска на этапе ротации. Новые сервисные билеты перешли на `aes256k`.
2. **Клиент `client.admin`.** Новый ключ подготовили параллельно со старым. На время обновления клиентов мониторы принимали оба ключа. Первый отчёт помощника показывал десять сессий `client.admin` со старым ключом на трёх узлах. Список VM и подключений RBD на каждом узле помогал искать потребителей. Число сессий показывает соединения с мониторами, а подсказки по VM относятся к узлу в целом.
3. **Переподключение RBD.** В окне работ полностью остановили и заново запустили четыре работавшие VM и один LXC. Две уже остановленные VM оставили выключенными. Полная остановка освобождает прежние RBD-подключения. Обычная перезагрузка ОС внутри VM сохраняет процесс QEMU и может сохранить старый ключ. Для совместимой VM с новым keyring на целевом узле Proxmox также документирует живую миграцию. Для LXC на RBD нужен полный stop/start.
4. **Подтверждение ключа и ограничение шифров.** Проверили оставшиеся сессии, затем `--confirm-all-clients-refreshed` сделал новый ключ `client.admin` действующим и вывел из обращения старый. После `--restrict-ciphers` мониторы принимали только `aes256k`. При наличии внешних или отключённых клиентов перед этим шагом нужно проверить их отдельно, включая копии keyring. Помощник видит сессии, доступные мониторам.

Проверка плана помощника и настроек шифров в карте мониторов:

```bash
/usr/share/pve-manager/migrations/pve-cephx-rotate-service-keys
ceph mon dump -f json | jq '{auth_allowed_ciphers, auth_service_cipher}'
```

## Почему после ограничения шифров остался HEALTH_WARN

Проверка после ротации показала три OSD `up/in`, все 33 PG `active+clean` и переход постоянных ключей и новых билетов на `aes256k`. В последнем снимке 13 ноября в 23:53 МСК все три MON входили в кворум. Оставалось предупреждение `AUTH_INSECURE_ROTATING_SERVICE_KEY_TYPE` для четырёх групп временных ключей старого типа — `mon`, `mds`, `osd` и `mgr`.

MON хранят несколько поколений временных сервисных ключей, чтобы обслуживать ранее выданные билеты. В этом кластере `auth_service_ticket_ttl` составлял 3600 секунд. Поколения истекают по очереди, поэтому предупреждение может сохраняться несколько часов. Для этого кластера выбрали штатное истечение ключей. Принудительный сброс инвалидирует ранее выданные билеты.

```bash
ceph config get mon auth_service_ticket_ttl
ceph health detail
ceph -s
```

Переход в `HEALTH_OK` после истечения временных ключей журналом этого окна работ не подтверждён.
