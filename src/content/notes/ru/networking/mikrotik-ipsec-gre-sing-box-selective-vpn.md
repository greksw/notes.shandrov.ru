**Дата:** 6 ноября 2026 года  
**Статус:** пилот на одном клиентском компьютере; развёртывание на всю площадку не выполнялось.

## Задача

На первой площадке уже работал MikroTik с IPsec site-to-site и отдельным VPN-каналом для выборочных направлений. Требовалось перенести часть пользовательского трафика на существующий Linux-шлюз с **sing-box**, расположенный на второй площадке, не изменяя основной маршрут в интернет, DNS инфраструктуры Active Directory и правила для остальных пользователей.

Целевые условия:

- направление только выбранных доменов/IP через отдельную схему, а не full-tunnel;
- сохранение обычного WAN и прежнего VPN-канала на время пилота;
- DNS для проблемных доменов через зашифрованный upstream;
- отсутствие прямого широкого доступа пользователей удалённой площадки в сеть второй площадки;
- наблюдаемые, воспроизводимые тесты на клиенте, MikroTik и Linux.

Этот кейс описывает **фактически полученное состояние**, а не универсальный скрипт автоматического развёртывания. Все имена узлов, подсети, адреса, номера VLAN, имена интерфейсов, аккаунтов и названия локальных правил ниже **заменены условными**. Адреса в диапазоне `10.0.0.0/8` используются как иллюстративный пример, а не отражают реальную адресацию площадок. Команды служат для иллюстрации логики и не предназначены для копирования в производственную сеть без адаптации.

## Архитектура

Три основных компонента:

| Компонент | Роль | Условный адрес / интерфейс |
|---|---|---|
| `site-a-gw`, RouterOS 7 | Шлюз удалённой площадки, PBR и DNS FWD | VLAN 10: `10.10.10.1` |
| `site-b-gw`, RouterOS 7 | Межплощадочная связность и передача выбранного трафика на Linux | VLAN 20: `10.20.20.1` |
| `vpn-gw`, AlmaLinux | Локальный VPN-шлюз на sing-box | `10.20.20.61` |

Условный тестовый клиент: `10.10.10.192`. На первой площадке работают контроллеры домена AD/DNS; клиент обращается к AD DNS, а тот пересылает внешние запросы на локальный маршрутизатор.

```text
                          ПЛОЩАДКА A

 Windows 10.10.10.192
          |
     VLAN 10
          |
   site-a-gw (RouterOS)
      |             \
      |              \  DNS для выбранных доменов
      |               \  AD DNS -> site-a-gw FWD
      |                \
      |   IPsec S2S     \ IPsec S2S: запросы к 10.20.20.61:53
      | + GRE overlay    \
      v                    v
   site-b-gw -------------+---------------- ПЛОЩАДКА B
      |
      | маршрутизация выбранных назначений
      v
 vpn-gw (10.20.20.61)
      |  sing-box TUN: пользовательский трафик
      |  отдельный sing-box DNS:53
      |
      +-- TCP  -> NaiveProxy -> внешний VPN-сервер
      +-- UDP  -> Hysteria2  -> внешний VPN-сервер
      +-- DNS  -> DoH 1.1.1.1:443 через Hysteria2
```

**Важно:** DNS-запросы к `10.20.20.61:53` передаются по существующей связности IPsec между площадками. Пользовательский трафик к выбранным публичным IP идёт по GRE поверх защищённого межплощадочного канала. Эти два пути связаны логически, но не являются одним и тем же интерфейсом.

GRE-параметры проверенного оверлея:

| Параметр | A | B |
|---|---|---|
| GRE inner IP | `172.20.250.1/30` | `172.20.250.2/30` |
| GRE outer IP | `10.10.10.1` | `10.20.20.1` |
| Интерфейс | `gre-site-a-b` | соответствующий GRE |
| MTU | `1300` | `1300` |

До включения PBR обмен ICMP по GRE подтверждён в обе стороны: 5/5 ответов, задержка порядка 7 мс. MTU 1300 выбран для оверлея; отдельный полный PMTU-аудит всех протоколов в рамках этого пилота не проводился.

## 1. Выборочная маршрутизация в RouterOS

На первой площадке используется отдельная таблица маршрутизации `to-REMOTE-VPN`. Её маршрут направляет отмеченные пакеты к GRE next-hop `172.20.250.2`; предусмотрен blackhole fallback, чтобы при потере основного маршрута не отправлять отмеченные пакеты в обычный WAN. **Фактический отказ GRE с проверкой поведения fallback пока не моделировался.**

Разделение трафика строится на двух списках:

- `VPN-PILOT-SRC` — источники, которым разрешён новый маршрут. Во время теста в нём только `10.10.10.192`.
- `VPN-TARGETS` — адреса назначения, которые следует направить через VPN. Список содержит статические BGP-derived префиксы и динамические IP, полученные из DNS-ответов.

Суть активного правила `mangle`:

```routeros
/ip firewall mangle
add chain=prerouting in-interface-list=LAN \
    src-address-list=VPN-PILOT-SRC \
    dst-address-list=VPN-TARGETS \
    dst-address-type=!local \
    action=mark-routing new-routing-mark=to-REMOTE-VPN \
    passthrough=no \
    comment="SITE-A-B | USERS VLAN10 selective routing"
```

Для пакетов, уходящих в GRE, применяется отдельный SNAT к адресу `172.20.250.1`:

```routeros
/ip firewall nat
add chain=srcnat \
    src-address-list=VPN-PILOT-SRC \
    dst-address-list=VPN-TARGETS \
    out-interface=gre-site-a-b \
    action=src-nat to-addresses=172.20.250.1 \
    comment="SITE-A-B | USERS VLAN10 SNAT"
```

Это **иллюстрация проверенных условий правил**, а не команда для повторного выполнения на уже настроенном маршрутизаторе. В реальном firewall существенен порядок относительно существующих `mangle`, общего NAT, IPsec NO-NAT и прежнего VPN-канала. Повторное добавление создаст дубликат.

Проверка без изменения конфигурации:

```routeros
/ip firewall mangle print detail where comment="SITE-A-B | USERS VLAN10 selective routing"
/ip firewall nat print detail where comment="SITE-A-B | USERS VLAN10 SNAT"
/ip firewall mangle print stats where comment="SITE-A-B | USERS VLAN10 selective routing"
/ip firewall nat print stats where comment="SITE-A-B | USERS VLAN10 SNAT"
/ip firewall address-list print where list="VPN-PILOT-SRC"
```

## 2. Разделение DNS и пользовательского трафика

### Почему обычного DNS оказалось недостаточно

Первые проверки некоторых доменов возвращали CNAME без конечной A-записи или вовсе не возвращали ответ. Для сервисов с несколькими CDN-доменами это особенно заметно: HTML основного сайта загружается, а часть статических ресурсов нет.

При этом DNS для рабочих станций проходит через корпоративный AD:

```text
Windows -> AD DNS -> site-a-gw MikroTik DNS FWD -> site-b-gw -> sing-box DNS -> DoH/Hysteria2
```

Менять настройки DNS на всех компьютерах и создавать conditional forwarder на контроллерах домена не потребовалось.

### Отдельный DNS-процесс на Linux

На `vpn-gw` создан отдельный системный сервис `vpn-dns-proxy.service`, не затрагивающий основной `sing-box.service`.

В конфигурации отдельного экземпляра sing-box:

- DoH-сервер Cloudflare: `1.1.1.1:443`, путь `/dns-query`;
- исходящее подключение DNS с `detour: hy2-out`;
- приём DNS по UDP/TCP на `10.20.20.61:53` и локально на `127.0.0.1:1055`;
- обработка DNS-запросов через правило `hijack-dns`;
- сервис работает от отдельной учётной записи `vpn-dns` с минимально необходимой привилегией для привязки порта 53.

Сервис защищён systemd-параметрами `NoNewPrivileges`, `PrivateTmp`, `ProtectHome` и разрешённой capability `CAP_NET_BIND_SERVICE`. На AlmaLinux дополнительно разрешён входящий UDP/TCP 53 **только от межплощадочного источника**, а не для всего интернета.

Проверка:

```bash
systemctl is-active sing-box vpn-dns-proxy
systemctl is-enabled vpn-dns-proxy
firewall-cmd --check-config
ss -lntup | grep ':53'

dig @10.20.20.61 -p 53 chatgpt.com A +short
journalctl -u vpn-dns-proxy -n 30 --no-pager
```

В журнале отдельного экземпляра подтверждена отправка DNS к `1.1.1.1:443` через `outbound/hysteria2[hy2-out]`.

### Маршрутизатор как DNS-клиент: ловушка с source IP

При запросах непосредственно с `site-a-gw` исходным адресом неожиданно становился `10.10.99.2` — адрес другого интерфейса маршрутизатора. Существующие IPsec policies для межплощадочной сети не включали этот источник, поэтому запросы к `10.20.20.61:53` не проходили.

Проблема решена **двумя точечными правилами SNAT** для UDP/TCP 53 с конкретной парой адресов (`10.10.99.2` → `10.10.10.1` при назначении `10.20.20.61`). Общий source NAT не менялся. Контрольные запросы прошли, а логи Linux показали источник `10.10.10.1`.

Полезный диагностический вывод: успешная IPsec-связность между подсетями сама по себе не гарантирует прохождение **router-originated** пакетов — необходимо проверить, какой source IP выбирает сам MikroTik.

## 3. Именованные DNS Forwarder и динамический address-list

На первой площадке настроен DNS Forwarder:

```routeros
/ip dns forwarders print detail where name="DNS-VIA-HY2"
```

Он указывает на `10.20.20.61`. Для отдельных доменных зон созданы/скорректированы FWD-записи с параметрами:

```text
forward-to=DNS-VIA-HY2
match-subdomain=yes
address-list=VPN-TARGETS
```

В ходе проверки на выделенный upstream переведены FWD-зоны двух целевых веб-сервисов и их CDN. Остальные зоны на этом этапе массово не переключались. Конкретные внешние домены исключены из публичного описания.

Проверка конфигурации на маршрутизаторе:

```routeros
/ip dns forwarders print detail where name="DNS-VIA-HY2"
/ip dns static print detail where type=FWD
/ip dns cache print detail
```

При необходимости вывод ограничивают именами конкретных FWD-зон. В публичной статье их не приводим.

С помощью `address-list` RouterOS добавляет полученные из DNS-ответов адреса в `VPN-TARGETS`. Срок жизни динамической записи связан с DNS TTL и параметром `address-list-extra-time`. Статические префиксы при этом продолжают действовать независимо от DNS-кеша.

При проверке обнаружилось, что часть CDN-адресов уже покрывается ранее импортированными статическими префиксами. Поэтому отсутствие **отдельной** динамической записи для CDN не означает отсутствие маршрута. Кроме того, точная проверка `address=...` не показывает охватывающий CIDR-префикс; это надо учитывать при диагностике.

## 4. Проверка на Windows и MikroTik

Ключевое правило диагностики: **HTTP 200 само по себе не доказывает, что трафик прошёл через новый VPN**. Сначала нужно подтвердить IP тестовой машины, затем сравнить счётчики маршрутизации и проверить внешний IP на целевом ресурсе.

Проверка IP пилотного клиента:

```powershell
Get-NetIPAddress -AddressFamily IPv4 |
    Where-Object { $_.IPAddress -like '10.10.10.*' } |
    Select-Object InterfaceAlias, IPAddress, PrefixLength
```

В обезличенном примере это `10.10.10.192/24` — единственный адрес, включённый в `VPN-PILOT-SRC`.

Для DNS-проверки через MikroTik и AD DNS использовались реальные имена выбранных сервисов и их CDN. Ниже — **шаблон с условными IP** для повторения диагностики: замените `<домен-сервиса>` и `<домен-CDN>` на фактические FQDN. Значения в угловых скобках не являются рабочими адресами.

```powershell
Resolve-DnsName -Name '<домен-сервиса>' -Type A -Server 10.10.10.1
Resolve-DnsName -Name '<домен-CDN>' -Type A -Server 10.10.20.11
```

Проверка HTTPS без системного прокси на общедоступном сервисе:

```powershell
curl.exe -4 -sS -L --http1.1 `
    --noproxy "*" `
    --connect-timeout 10 --max-time 30 `
    -o NUL `
    -w "HTTP=%{http_code} IP=%{remote_ip} SIZE=%{size_download} TIME=%{time_total}s`n" `
    https://chatgpt.com/
```

В пилоте получены следующие результаты:

| Проверка | Результат | Что подтверждено |
|---|---|---|
| Веб-сервис A, HTTPS | HTTP 200, ~369 КБ за 2,15 с | HTTPS работает |
| Веб-сервис A, браузер | Страница открылась | Основной интерфейс доступен |
| Веб-сервис B, HTTPS | HTTP 200, ~381 КБ за 2,15 с | HTTPS работает |
| Веб-сервис B, браузер | Страница открылась | Основной интерфейс доступен |
| CDN веб-сервиса B | CNAME + A | CDN DNS работает через MikroTik и AD |
| `chatgpt.com` | HTTP 200 за 2,11 с | Основной HTTPS работает |
| `auth.openai.com` через `curl -I` | HTTP 403, `Cf-Mitigated: challenge` | Cloudflare потребовал проверку; это не равнозначно поломке сети |

Для веб-сервиса B счётчики после теста браузера изменились так:

```text
mangle:   5 061 -> 6 147  (+1 086 пакетов)
GRE SNAT:    21 ->    27  (+6 совпадений NAT)
```

Количество совпадений NAT не обязано расти на каждый пакет: NAT-правило преимущественно срабатывает при создании соединений. Рост обоих счётчиков во время теста вместе с успешной загрузкой страницы — сильный признак использования выбранного маршрута, хотя глобальные счётчики не доказывают путь **каждого** отдельного HTTP-запроса.

### Отдельная проверка реального VPN-выхода ChatGPT

DNS некоторых имён возвращал нетипичные для ожидаемой схемы адреса. Это не было принято за доказательство DNS-подмены: дополнительно проверили реальный HTTPS и внешний IP, не прописывая статические адреса.

```powershell
curl.exe -4 -sS --noproxy "*" `
    --connect-timeout 10 --max-time 20 `
    https://chatgpt.com/cdn-cgi/trace |
    Select-String -Pattern '^(ip|colo)='
```

Получен ожидаемый внешний IP VPN-шлюза. Данные о географии и публичном IP намеренно не публикуются. Это подтверждает, что **именно запрос к `chatgpt.com` вышел через новый VPN**, а не через прямой WAN удалённой площадки. Фактический публичный IP и география VPN-узла в статье намеренно не раскрыты.

Адреса `auth.openai.com` и `challenges.cloudflare.com` были обнаружены в `VPN-TARGETS` как динамические записи. Однако полноценный вход в учётную запись ChatGPT через браузер к концу пилота **не подтверждён**; HTTP 403 на HEAD-запрос к `auth.openai.com` с `Cf-Mitigated: challenge` нельзя интерпретировать как окончательный отказ авторизации.

## 5. Ограничение доступа и эксплуатационные риски

В этой архитектуре особое внимание уделено тому, чтобы удалённая площадка не получила транзитный доступ ко всей сети второй площадки:

1. В `VPN-PILOT-SRC` добавлен лишь один клиент; остальные пользователи продолжают использовать прежние маршруты.
2. Разрешение на DNS с первой площадки к Linux ограничено конкретным назначением `10.20.20.61:53`, протоколами UDP/TCP и источником, проходящим межплощадочную IPsec-политику.
3. Linux firewalld дополнительно ограничивает доступ к DNS. Основной sing-box и отдельный DNS-процесс запускаются независимыми systemd-службами.
4. Маршрут таблицы `to-REMOTE-VPN` имеет blackhole fallback; серверный `vpn-egress-guard.service` активен. Но **реальный тест отказа GRE, Linux и внешнего VPN-сервера не проводился**, поэтому fail-closed пока следует считать настроенным, а не проверенным под отказом.
5. Прежний VPN-канал не отключался: он остаётся частью действующей инфраструктуры до отдельного этапа миграции.

Отдельные пункты для последующей эксплуатации: контроль счётчиков и DNS TTL, сроков жизни динамических IP, журналов `vpn-dns-proxy`, доступности UDP/TCP 53 только из нужных подсетей, MTU/PMTU и корректной обработки FastTrack для PBR-трафика.

## Итог

Построен и проверен **выборочный межплощадочный маршрут**:

```text
клиент площадки A -> MikroTik PBR -> IPsec/GRE -> site-b-gw -> Linux sing-box -> VPN-сервер
```

Для выбранных доменов отдельно настроен DNS через:

```text
AD DNS -> MikroTik FWD -> IPsec -> sing-box DNS -> DoH/Hysteria2
```

**Подтверждено:** корректная DNS-разрешимость двух выбранных веб-сервисов и их CDN, загрузка сайтов в браузере с пилотного компьютера, рост счётчиков GRE-маршрутизации, HTTPS ChatGPT и его выход через ожидаемый публичный VPN IP.

**Пока не подтверждено:** полноценная авторизация и работа интерфейса ChatGPT после входа, отказоустойчивость при недоступности GRE или внешнего VPN-сервера, работа других целевых сервисов и перевод всей пользовательской сети. Все эти проверки должны выполняться **до** отключения прежнего VPN-канала и расширения списка пилотных источников.
