В [первой части](/ru/notes/storage-backup/truenas-picasso-ez3d2009-pilot-part-1/) проверяли чтение исследований из центрального хранилища. [Во второй](/ru/notes/storage-backup/truenas-picasso-ez3d2009-merged-dataset-part-2/) собрали локальные базы и проверили объединённую копию. После этого оставалось проверить, как врач добавляет **новое** исследование и затем открывает его из той же общей базы.

В ходе приёмки два новых пакета прошли всю цепочку до рабочего 3D в Picasso Viewer. Один отправили из PowerShell, второй — через ярлык. На отдельной станции проверили автоматическую настройку ярлыков при входе в Windows. Подтверждение относится к этим сценариям и рабочим местам.

## Схема взаимодействия

![AD и GPO устанавливают отправщик на Windows. Windows пишет пакет в персональный SMB Inbox. Импортёр на TrueNAS читает входной снимок ZFS и публикует проверенное исследование. Picasso Viewer читает Production по SMB.](/images/notes/storage-backup/picasso-importer-flow.png)

На рабочей станции ярлык подготовки открывает личный каталог `Drop`, а ярлык отправки передаёт одну папку экспорта в персональный `Incoming` по SMB. Пользователь получает право записи в свою очередь. Изменения в общем архиве выполняет Python-импортёр локально на TrueNAS. Picasso Viewer читает опубликованный архив через отдельный SMB-ресурс с доступом только для чтения.

## Почему успешного копирования DICOM оказалось мало

Первое новое задание с 400 DICOM было принято сервером и получило `IMPORTED_VERIFIED`, но исследование не появилось в списке Viewer. В полном экспорте был оригинальный `Default.npj`. Когда к копии тех же DICOM добавили этот файл из того же экспорта, Viewer показал исследование и открыл 3D.

Клиент и сервер после этого перешли на пакет из плоского набора DICOM и одного оригинального `Default.npj`. Клиент берёт снимки либо из корня экспорта, либо из дерева `Data`. Он останавливается, если снимки найдены в обоих местах или если при выравнивании структуры совпадут имена файлов. Служебные файлы экспорта пропускаются. Проект передаётся побайтно, сервер проверяет его размер и SHA‑256. Связь проекта с DICOM обеспечивается тем, что оба взяты из одной исходной выгрузки. Формат проекта разбирает приложение поставщика.

Это исправление подтверждено для новых отправлений. Периодическая ошибка `Can not open ProjectFile` из первой части была отдельным наблюдением раннего пилота.

## Что происходит между отправкой и появлением в Viewer

| Этап | Что проверяется |
|---|---|
| Windows готовит пакет | Исходные файлы сверяются с сетевой копией по SHA‑256. Пока копирование идёт, папка имеет временное имя. После сверки клиент создаёт маркер готовности и атомарно присваивает каталогу итоговое имя. |
| TrueNAS принимает задание | Проход cron каждые пять минут выбирает одно готовое задание. Импортёр фиксирует вход снимком ZFS и сверяет собственные манифесты живого пакета и снимка. |
| Импортёр проверяет UID | Study Instance UID и SOP Instance UID сверяются со всей существующей базой. Дубликат завершается без создания второй папки. Пересечение UID требует разбора. |
| Импортёр публикует | Файлы готовятся вне каталога Viewer. Сервер проверяет хэши и права доступа, затем выполняет переименование с запретом замены назначения. Итог обработки сохраняется отдельно от рабочей папки исследования. |
| Врач открывает исследование | Запись появляется в общем списке. Приёмка завершается проверкой срезов и вращения 3D с того же источника, которым пользуются врачи. |

Сервер проверяет состояние пулов, репликации и ожидаемый SMB-режим до работы с очередью. Один из входных барьеров первоначально сравнивал точную строку версии TrueNAS. После обновления очередной импорт остановился на проверке версии. В рабочем варианте версия пишется в журнал, а допуск строится на состоянии нужных ресурсов. Источник сохраняется, а у успешной публикации остаются входной, pre- и post-снимки, а также результат задания. Успех импорта и завершение последующей репликации можно проверить отдельно.

## Как два ярлыка дошли до рабочего стола

Компьютерная политика при старте ставит отправщик и иконки в защищённый `Program Files`. Пользовательская политика при новом входе проверяет защищённую копию и настраивает ярлыки в профиле пользователя.

При ручной проверке Windows PowerShell 5.1 с `RemoteSigned` отклонил неподписанный сценарий, запущенный по UNC. Обычный сценарий Logon теперь проверяет SHA‑256 временной локальной копии пользовательской настройки и запускает её с `RemoteSigned`. Для миграции прежнего ярлыка проверяются известная команда отправки и штатный PowerShell. Путь и хэш защищённого отправщика проверяются перед записью ярлыка.

Для проверки самой настройки достаточно режима `Plan`, который распознаёт старый ярлык без его замены. Автоматический запуск проверяется по свежей записи `APPLY` после интерактивного входа. Проверка по SSH годится для `Plan`, но не заменяет вход в рабочий стол.

## Что подтвердилось в работе

| Проверка | Результат |
|---|---|
| Отправка из PowerShell | 456 DICOM и один `Default.npj`. Сервер вернул `IMPORTED_VERIFIED`. Исследование открылось из Production, 3D вращалось. |
| Отправка двойным щелчком | 400 DICOM и один `Default.npj`. Подтверждены передача, серверный импорт и открытие нового исследования из Production. |
| Сценарий входа на другой станции | После нового входа журнал подтвердил запуск настройки и проверку двух ярлыков. |

Отправщик сообщает о готовности пакета, серверный JSON — о публикации, а проверка в Viewer — о пригодности опубликованного набора для работы в приложении. Эти три события полезно записывать отдельно. Людям, которые проверяют очередь, достаточно номера задания и времени отправки. Снимки, имена пациентов, реальные пути, учётные записи и необработанные логи в статье не используются.
